# Repository Guidelines
## Project Structure & Module Organization
happyStock splits work across two apps. `frontend/` hosts the Next.js 15 client: routes live in `src/app`, shared UI in `src/components`, state stores in `src/store` and `src/stores`, and API helpers under `src/services`. `backend/` contains the FastAPI stack: `main.py` is the entry point, `routers/` expose HTTP endpoints, `services/` hold domain logic, and `schemas/` define Pydantic contracts. Specifications in `specs/00*/` document ongoing initiatives, architecture notes sit in `doc/`, and `sql_scripts/` keeps repeatable database helpers.
## Build, Test & Development Commands
Start Redis first (`./start_redis.sh` or `start_redis.bat`) so rate limiting and token flows succeed. Inside `backend/`, run `pipenv install --dev` followed by `pipenv run uvicorn main:app --reload` to serve the API at http://localhost:8000; seed local data with `pipenv run python scripts/init_db_tables.py` when needed. In `frontend/`, install dependencies via `npm install`, launch the dev server using `npm run dev` (http://localhost:3000), and prepare production bundles with `npm run build`. Root-level `start.sh` or `start.bat` orchestrates Redis, API, and UI for quick smoke checks.
## Coding Style & Naming Conventions
Follow PEP 8 for Python files, keep modules snake_case, and prefer descriptive verb-first route names (`/auth/reset-password`). Type hints are required for new backend services and schemas. The Next.js codebase uses TypeScript with two-space indentation; write React components as PascalCase files exporting default functions, keep hooks camelCase, and group Tailwind utility classes by layout, color, then state to match existing files. Run `npm run lint` before every push to satisfy the shared ESLint and Tailwind rules.
## Testing Guidelines
Backend test suites belong in `backend/tests/`; mark async cases with `pytest.mark.asyncio` and hit the Redis-powered paths when possible. Execute `pipenv run pytest backend/tests -v` after installing the pytest extras referenced in `specs/002-virtual-market-full/quickstart.md`. Maintain lightweight smoke scripts such as `pipenv run python test_auth.py` for targeted troubleshooting. Frontend validation currently depends on linting plus the manual flows in `BROWSER_TEST_GUIDE.md`; add automated Playwright specs under `frontend/tests/` as they are introduced and gate merges on their CI passes.
## Commit & Pull Request Guidelines
Commits follow the short conventional prefixes shown in `git log` (`feat:`, `fix:`, `chore:`) and may scope surfaces (`feat(frontend): optimize hero layout`). Keep subject lines under 72 characters and favor present-tense verbs. Pull requests should explain the change, list affected routes or components, link the tracking issue, and attach UI screenshots or API traces when behavior shifts. When a PR spans both apps, request reviews from the corresponding maintainers and confirm `start.sh` runs cleanly before assigning reviewers.
## Environment & Configuration
Copy `backend/.env.example` to `.env`, set database, Redis, and SMTP credentials, and leave secrets out of version control. The frontend expects a populated `.env.local` for API URLs and feature toggles; commit only placeholder values. SQLite artifacts (`backend/db.sqlite3`, `backend/virtual_market.db`) are disposable and should be regenerated through scripts instead of edited directly.
